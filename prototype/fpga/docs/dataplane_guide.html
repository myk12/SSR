SECTION 0The mental model in one page

SSR is synchronous state-machine replication: a small cluster of nodes (three here) that all want to apply the same sequence of inputs in the same order. Instead of electing a leader and running a message-driven protocol, SSR divides time into fixed rounds of 4 000 ns, numbered from the PTP clock that every node shares. In every round every node does the same three things, at the same time as everyone else:

  1. Propose. Broadcast the bytes its host wants replicated, as 4 096-byte Ethernet frames called fragments — whenever the host hands them over, until a cutoff near the end of the round.
  2. Observe. Count, per peer, how many of its fragments for the round arrived, as an unbroken prefix 0, 1, 2 …; count, for itself, how many it sent. That is one byte per node — the ack vector.
  3. Report. Broadcast the ack vector in the next round's control frame, so that everyone can compare vectors and see whether they hold the same thing. A peer whose vector equals ours is a witness.

A round is committed when a majority of the nodes, ourselves included, are witnesses: they reported the same vector for it. That vector then says, for every node, how many of its fragments for that round are part of the replicated history — its committed prefix. Nothing is retried and nothing is negotiated; a node that holds something the majority does not stops (halts) rather than continue in disagreement. That is the whole protocol. The rest of this document is about the machinery that moves the bytes and counts them, and about how the result reaches the host.

Why bytes go first and the decision goes later

The design is called speculative delivery. A peer's fragment is DMA'd into host memory the moment it arrives, before anyone knows whether the round will commit. The alternative — hold a round's payload on chip until the verdict — would need on-chip storage proportional to round depth × nodes × payload, and would add the whole decision latency to the data path. Instead the on-chip buffer is sized by one frame and the PCIe drain time, the host gets the bytes early, and the verdict record is fenced behind the DMA completions so it can never describe a page that has not landed.

SECTION 1The map: every module, every bus

The dataplane is a Corundum application block: a module that mqnic instantiates inside the NIC and hands five things — a control-register bus, a DMA read descriptor interface, a DMA write descriptor interface, the segmented RAM ports those DMAs read and write, and the interfaces' transmit and receive AXI-Stream. Everything SSR does is built from those five. The AU200 has two interfaces, one per QSFP28 cage, so the streams arrive two lanes wide: SSR takes the lane named by SSR_IF_INDEX (a localparam in the app block, 0 by default) and wires the other straight through, where it stays an ordinary NIC port. The wrapper is ssr_dataplane.v; every other file is instantiated inside it. Every SSR file and module is named ssr_<name>, file name = module name, so none of them can collide with Corundum's own tx_engine, rx_engine or dma_* modules; the figures drop the prefix to fit.

SECTION 2Time: the round and the two-round pipeline

Every node has a PTP-disciplined time-of-day clock, and ssr_core.v derives the round number from it: round_id = ToD_ns / P_SLOT_DURATION_NS. The ToD is ptp_sync_ts_tod, the 96-bit {sec[47:0], ns[31:0], fns[15:0]} that mqnic_ptp hands the app block already in its clock domain; the wrapper takes seconds from bits 95:48 and nanoseconds from 47:16, with P_SLOT_DURATION_NS = 4000. Because the clocks agree to within tens of nanoseconds, all nodes enter round R at (almost) the same instant, and there is no message that says "round R begins" — time itself does. The core raises a one-cycle round_start_pulse at every boundary; it shifts the core's pipeline and opens the presence tracker's slot for the new round. The transmit side gets two things from the core: a start pulse 332 ns into the round, and a level, o_tx_pay_open, that stays high from the boundary until the transmit cutoff.

The round used to be divided into per-node transmit slots (TDMA). It is not any more. Every node sends its control frame at the same offset into the round and shares the receiver by pacing: after every fragment a node waits N−2 frame-times, so N−1 peers together never exceed the line rate at any one receiver. Fragments may start anywhere in a window that runs from just after our control frame to the transmit cutoff; nothing about them is planned or announced in advance. The result is a round with a few fixed instants and one paced window:

The two-round pipeline

A round's bytes arrive during the round. Its ack vectors — what each node holds of it — cannot go out until the next round, because a node only knows what it holds, and how much it sent, once the round is over. And the decision needs the vectors. So the core keeps two stages, CURRENT and PREVIOUS, shifts them at every boundary, and decides PREVIOUS at the control deadline of the round after — 646 ns plus eight settle cycles into it — which is the first instant every witness is known and the last instant anything could still change that (a control frame after the deadline is dropped):

Worked example

Round R = 2 750 000 opens at ToD 11 000 000 000 ns. We send 2 fragments; node 1 sends 3 and all three are stored here by 2 110 ns; node 2 sends none. At the boundary into R+1 our counts for R are final: our ack vector is [2, 3, 0] ("I sent 2, I hold 3 of node 1's and 0 of node 2's"). Our R+1 control frame carries it. During R+1 we receive node 1's and node 2's control frames for R+1, each with their vector about R — also [2, 3, 0] if they lost nothing — and each one that matches ours makes its sender a witness. At R+1's control deadline — 646 ns plus 32 ns of settle into R+1, 4 678 ns after R opened — the core has three witnesses, more than the quorum of 2, and commits R: two pages of ours, three of node 1's, none of node 2's.

SECTION 3The frame is a page

Everything that crosses the wire is one frame format, defined once in rtl/ssr_packet.vh and mirrored in tb/mqnic_core_pcie_us/ssr_packet.py. The design rule is that a frame is exactly one host page: 64 bytes of header followed by up to 4 032 bytes of payload, 4 096 in all. That single choice removes a lot of machinery — the header is one 512-bit beat, so the payload starts on a beat boundary and no byte shifter is needed anywhere; a received frame is staged in one 4 KiB slot and moved to the host with one DMA descriptor; and every host page carries its own header on top, so a page says which node, round and fragment it is without any side table. How many of a node's pages count is not on any page; that is the verdict record's job (Section 11).

Two kinds of frame

CONTROL — kind 1, one per node per round, always sent

Header only: length = 0, frag_idx = 0, tlast on the header beat. It looks only backward: its ack is evidence about the previous round, and nothing in it is about the round it opens. A node with nothing to propose still sends it; that is how it stays visibly alive and keeps its place in everyone's sound set.

PAYLOAD — kind 2, zero or more per node per round

One fragment. ack = 0; length is 1..4032; frag_idx < P_FRAGS_PER_ROUND, numbered 0, 1, 2 … in the order the sender sends them. Says nothing about the protocol — it is bulk data addressed by (round_id, node_id, frag_idx), which is exactly the tuple that later becomes its page address. How many fragments the round has is on no frame of that round: it travels in the sender's next control frame, as ack[sender].

Why an index and not a byte offset

A node's payload for a round is a run of proposal entries, one per fragment, each carrying at most 4 032 bytes. 4 032 is not a power of two, so a byte offset would need a division to become a page number; a fragment index becomes a page number with a shift. The index is also what the receiver counts with: a fragment adds to the count only if its frag_idx is the next one expected (Section 9). The fabric never looks inside an entry; the application's one rule is that a proposal never spans two entries, because the cluster may commit a prefix of a node's fragments (Section 10) and a prefix must not end in half a proposal.

SECTION 4Transmit: proposals become fragments

The transmit path is three modules in a line. The host writes proposals into a ring in its own memory and rings a doorbell; ssr_proposal_dma_reader pulls them into ssr_proposal_buffer, an on-chip ring of 4 KiB slots; and ssr_tx_engine turns each round's start pulse into one control frame, and then sends a fragment whenever the buffer offers a slot, paced, until the transmit cutoff. Nothing is planned: a proposal the host posts halfway through a round goes out in that round, and what this node sent is reported afterwards, in the next control frame. (Before count acks the engine counted the buffer's slots at the control frame and announced that many; anything posted later waited a full round.)

4.1 The host's proposal ring and ssr_proposal_dma_reader

A proposal entry in host memory is one 4 096-byte block laid out exactly like the frame it becomes: the host leaves bytes 0..63 empty — ssr_tx_engine will write the frame header there — and puts at most 4 032 bytes of proposals at offset 64 — one or more whole proposals, never part of one, since a proposal never spans two entries (Section 3). So an entry carries 4 032 bytes, not 4 096, and the 64 bytes are padding on purpose: a proposal entry, a wire frame and a delivered page are one layout, and the host reads its own proposal (its region of the payload ring is never written) with the same parser and the same offset as a peer's page.

The entries live in a ring of 2^d entries, the commit path run backwards: its base and depth are programmed once, and entry i is at base + ((i mod 2^d) << 12) — a shift, no stride, no count. To propose, the host writes entries at its producer index and then writes the new index to PRODUCER: one posted MMIO write, the doorbell. ssr_proposal_dma_reader keeps two indices of its own, both free-running counts of entries: FETCH (reads issued) and CONSUMER (entries whole in the buffer, in order). It issues a 4 096-byte read for entry FETCH whenever FETCH ≠ PRODUCER, the buffer has a free slot and fewer than four reads are out — a 4 KiB read from host memory takes a microsecond or more, and one at a time could not keep up with five entries a round. Each read's tag is DMA_TAG_PROP | slot, so its completion names its slot. The DMA read engine writes the bytes directly into the buffer's RAM through the segmented write port; the reader never touches data.

Flow control. An entry below CONSUMER may be overwritten, so the host posts only while producer − consumer < 2^d. CONSUMER is also in every verdict record (proposal_consumer, Section 11), which the host is polling anyway, so the fast path has no MMIO read at all.

4.2 ssr_proposal_buffer: eight slots, beats 1..63 go out

The buffer is a ring of RAM_BUFF_SLOT_COUNT = 8 slots of RAM_BUFF_SLOT_BYTES = 4096, 32 KiB of block RAM. Because up to four reads complete in any order, it has three pointers: resv, the next slot to hand to a read; commit, the first slot whose read has not landed yet; and head, the slot being streamed to ssr_tx_engine. A completion sets its slot's done bit; commit walks forward over done bits and stops at the first slot still waiting, so slots become transmittable in ring order — the order the host posted them. A slot is popped when the last beat of its fragment has been accepted by the MAC. The buffer still exposes buf_slot_count, the number of committed slots, but the wrapper leaves it unconnected: the engine does not count slots, it only looks at whether the head slot's first beat is on offer. The buffer streams the head slot to ssr_tx_engine as 63 beats — beats 1 through 63 of the slot, skipping beat 0. Beat 0 is where the host left 64 empty bytes; the engine composes the frame header itself and sends it as beat 0, so beat k of the frame is beat k of the slot, byte for byte, with no shifting. The beats go out at one per cycle: the buffer issues RAM commands for beats 1..63 back to back, each to the segment that holds it (beat k is segment k mod 2 of a 1 024-bit row), and streams the responses in beat order, so a fragment is 64 back-to-back beats, 256 ns. (The first version waited for each beat before asking for the next — a quarter of that rate, and only three fragments fitted in a round.)

4.3 ssr_tx_engine: one pulse, a cutoff, a rate cap

The engine is a three-state machine — S_IDLE, S_HDR, S_PAYLOAD — driven by the core's i_tx_start_pulse (332 ns into the round) and i_tx_pay_open level (high from the boundary to the cutoff):

  1. At the pulse it latches round_id and run_id from the core and i_tx_ack from ssr_presence_tracker — our counts for the round that just ended — and resets frag_idx to 0. Nothing about the new round is decided here. If the round that just ended sent no fragment, TX_EMPTY increments.
  2. Control frame: S_HDR sends one beat with kind = CTRL, length = 0, frag_idx = 0, the ack at bytes 36..43, tlast. It always goes out, and it is the only thing that does. When it has left, pay_run is set: payload may follow.
  3. Skew gap: a P_PAY_GAP_CYCLES = 32 cycle countdown that started at the pulse must reach zero. It covers the case where an early node's payload could otherwise queue ahead of a late node's control frame in the switch.
  4. Fragments, as they come: whenever everything lines up at once — pay_run and i_tx_pay_open are high, the gap has run down, fewer than P_FRAGS_PER_ROUND have gone out this round, and the buffer is offering a slot's first beat right now — the engine takes that beat, S_HDR sends the header (kind = PAYLOAD, length = 4032, the next frag_idx, ack zero), and S_PAYLOAD streams the 63 rows, popping the slot on the last beat. The fragment is admitted on its first beat, so a flush cannot pull the slot out from under a header already composed for it, and the payload follows the header with no gap. o_local_sent pulses at admission — that is how ack[self] is counted. After each fragment the engine waits P_PACE_GAP_CYCLES = 82 cycles before the next.
  5. The cutoff. At TX_PAY_CUTOFF_NS = 3 341 ns the core drops o_tx_pay_open and pay_run is cleared. A fragment already on the wire finishes; nothing new starts; whatever is still in the buffer goes out next round, so nothing is dropped. pay_run is cleared whenever the level is low, not only by the next pulse: the level rises again at the boundary, a whole dead zone before our next control frame, and a slot waiting there would otherwise go out stamped with the round that had just ended (the integration bench's B6 found exactly that). A pulse that lands while a frame is still on the wire increments TX_OVERRUN but never truncates the frame. A pulse that cannot start a control frame increments TX_MISSED.
Worked example — round R at node 0

At 332 ns the pulse latches our ack about R−1 and the control frame goes out. Two slots are already committed in the buffer. The skew gap has run down during the control frame, so fragment 0 starts at 466 ns (o_local_sent: our count for R is 1) and ends at 793 ns; the pacing gap holds until 1 121 ns, fragment 1 runs to 1 448 ns, and the engine returns to S_IDLE with the buffer empty. Had the host posted a third entry at 2 000 ns, it would have gone out as fragment 2 at the next paced start after its read landed — any time up to 3 341 ns. As it is, TX_CTRL_FRAMES += 1, TX_PAY_FRAMES += 2, and our control frame in R+1 carries ack[0] = 2.

4.4 ssr_tx_mux: sharing the port with the host

The interface's transmit stream is shared between the NIC's own host traffic and SSR. The mux locks onto a source at the start of a frame and holds it until tlast, so frames never interleave. SSR frames are given priority at frame boundaries — a control frame delayed behind a jumbo host frame would miss the control deadline. Priority at frame boundaries is not quite enough for the last fragment of a round: one admitted at the cutoff can still wait behind a host frame already on the port, and behind a 9 KB frame it reaches a peer after that peer's boundary, is not counted there, and costs this node its round. That is an open item (docs/count_ack.md §10); it only matters when host traffic shares the SSR port. Corundum returns one transmit completion per frame, tagged with whatever the sender put in tuser; the mux tags SSR frames 0x4000 and swallows the completions carrying exactly that tag, because an SSR frame has no host descriptor to retire and forwarding it would corrupt the driver's completion queue. The top bit is the one bit SSR must not use: Corundum tags every host frame 0x8000 | descriptor index and acts only on completions with the top bit set. The completion's PTP timestamp is captured in TX_CPL_TS_* for measurement: PTP_TS_WIDTH bits zero-extended to 96, which on the AU200 is 48 bits of relative time, so TX_CPL_TS_2 reads 0.

SECTION 5Receive: the demux and the rejection ladder

On the way in, ssr_rx_demux looks at the ethertype of every frame on the interface's receive stream: 0x88B5 goes to ssr_rx_engine, everything else (ARP, TCP, a neighbour's LLDP) goes on to the host untouched. ssr_rx_engine then judges each SSR frame on its header beat alone and, if it passes, produces one of two things from it: for a control frame, a one-cycle trusted pulse to the core — "node k is a witness for the round being decided", and nothing else about the frame; for a payload frame, a tagged payload stream to the staging ring, whose tag the presence tracker also reads to count the fragment.

5.1 The ladder

The filter is a fixed sequence of tests. A frame is charged to the first test it fails and to no other, so every counter means exactly one thing. Every rejected frame is still consumed to its tlast (state S_DROP); stopping mid-frame would resynchronise the parser on a payload beat and corrupt everything after.

Worked example — a stale peer

Node 2 was rebooted with an old configuration and sends round-R frames with run_id = 0x76. Each passes ethertype, geometry, window, membership and sound-set tests, then fails run_id == 0x77: RX_RUN_DROP increments once per frame and the frame is eaten to tlast. So node 2's control frame never makes it a witness, and none of its fragments is counted: our ack byte for node 2 about R is 0, whatever node 2 says it sent. Unless node 1 saw the same, the disagreement is resolved at R+1's control deadline (Section 10).

5.2 The payload contract with ssr_payload_stage

An accepted payload frame is forwarded beat by beat before the engine knows the frame really ends where its length promised. So the contract is precise: o_pl_sof is a one-cycle pulse on the same cycle as the first payload beat, with the tag (node_id, round_id, frag_idx, length, and the full 64-byte header) beside it; the stage must latch the tag and accept that beat in the same cycle. When the frame ends, exactly one of o_pl_commit or o_pl_drop is raised, one cycle after the last beat, when the bus is structurally quiet — the stage writes the header row on commit into that quiet cycle, and rewinds its write pointer on drop. The beats carry tkeep only for information; the stage clamps by length. The same tag reaches ssr_presence_tracker, which latches (node, round, frag_idx) on sof and counts the fragment only when the stage reports it stored whole (Section 9).

SECTION 6Staging: sixteen slots and a completion-driven release

A frame cannot go from an AXI-Stream beat straight into a PCIe write. Corundum's DMA write engine is handed a descriptor naming an on-chip RAM (ram_sel, ram_addr) and reads the bytes out of it, in its own time. So every received fragment lands first in ssr_payload_stage: a ring of P_PAY_SLOT_COUNT = 16 slots of 4 096 bytes, 64 KiB of block RAM, which is also exactly the address space of one ram_sel.

What sizes the ring is worth being precise about. It is not sized by the round — the protocol never holds payload on chip until a decision. It is sized by how long PCIe takes to drain one frame, times how many frames can arrive meanwhile. A round brings at most (N−1) × P_FRAGS_PER_ROUND = 10 fragments; sixteen slots hold a round and a half, which is checked at elaboration (P_PAY_SLOT_COUNT ≥ (N−1) × P_FRAGS_PER_ROUND).

A slot is a frame is a page

Beat 0 of a slot is the frame's 64-byte header, exactly as it was on the wire; beats 1..63 are the payload. (Two beats share a RAM row: the header is segment 0 of the slot's first row, the first payload beat segment 1.) The header is written last, on the commit cycle, because until o_pl_commit the engine has not confirmed the frame ended where its length said. One descriptor then moves the whole slot to one host page, header on top.

Why the release waits for the completion and not the pop

The DMA write engine accepts a descriptor into its operation table and reads the staging RAM afterwards, asynchronously, over the cycles it takes to form the TLPs — under PCIe back-pressure that can be microseconds. If the pop released the slot, the next frame off the wire could overwrite it first, and the host would receive the next frame's bytes under this frame's header. The old serial commit writer never had this problem because it waited; several descriptors in flight is the whole point of this path, so the release has to come from the completion. The slot number travels round-trip in the tag pool's per-tag meta (Section 7) and comes back as i_done_slot.

What it does not do

It never back-pressures the wire: o_pl_ready is tied high, because the bytes are already on the wire and the MAC will not wait. When there is no free slot the frame is discarded and STAGE_FULL counts it. A discarded frame is not counted (Section 9), so our ack byte for that peer stops short of what the other nodes hold; the protocol treats that exactly like a frame lost in flight. PCIe falling behind the wire costs a peer its round, never the protocol its safety.

SECTION 7Pages out: the DMA writer and the tag pool

ssr_payload_dma_writer does one thing in one sentence: pop a slot off the stage's head, compute where in host memory those bytes belong, borrow a tag, hand the descriptor to the DMA engine; when the engine reports the tag done, return the tag and tell the stage which slot it may reuse. It stores nothing, keeps no state machine and never waits for a completion before issuing the next descriptor. A pop happens when four things are true in one cycle — the head has a frame, the pool has a tag, delivery is enabled, and the single output register is free — so the sustained rate is one descriptor per cycle if the engine takes them.

ssr_dma_tag_pool

Tags identify descriptors in flight. Corundum returns a status per descriptor carrying the tag it was given; with several descriptors outstanding at once, and completions in any order, each one needs a unique tag and something to remember what it belonged to. The pool hands out TAG_BASE with its low 4 bits replaced by a free id (0..15, on the data DMA), recognises a completion as its own when the upper bits match, and keeps two things per tag: the caller's meta and a unit number. The unit is whatever the caller wants to fence on — here round_id mod 4 — and o_unit_idle[u] is a registered "no tag of unit u is outstanding". o_high_water records the most tags ever outstanding at once, exposed in the delivery STATUS register so you can see how close the pool came to running dry.

SECTION 8Host memory: rings, regions, pages

The host owns two rings, allocated by the driver and told to the FPGA through PAYLOAD_BASE and VERDICT_BASE in the delivery block. Their geometry is fixed at build time and readable from GEOMETRY, so software never guesses.

The payload ring is indexed by round, then node, then fragment. Each node has a region of 2^P_REGION_SHIFT bytes per round — P_REGION_SHIFT = clog2(5 × 4096) = 15, so 32 KiB, of which 5 pages are usable — and a round's slot is N regions. The ring is 2^P_HOST_DEPTH_LOG2 = 256 rounds deep: about a millisecond of history at 250 000 rounds per second.

region_index = (R mod 256) × N + k
host_addr    = payload_base + (region_index << 15) + (f << 12)

R mod 256 is a bit slice, × 3 is a shift and an add, and the rest is wiring — the address is computed in the same cycle the head is popped, with no state in between.

The verdict ring

The second ring is simpler: 2^P_VERDICT_DEPTH_LOG2 = 256 records of 64 bytes, 16 KiB. Record number seq — counting from zero at reset and never repeating — lands at verdict_base + (seq mod 256) × 64. The host keeps the last seq it consumed and polls the next entry until its seq field shows the value it is waiting for; a 64-byte record is one PCIe write, so it lands whole and the field can be trusted the moment it changes. In the example, round R is the 18th commit since activation, so its record is seq = 17 at 0xA_0000_0000 + 0x440 = 0xA_0000_0440.

What the host does with a record

For each node k with present_set[k] set, read pages 0 .. frag_count[k]−1 from region ((round_id mod 256) × N + k), taking each page's meaningful length from the length field of the header on the page. commit_set does not gate the read (Section 11), and pages past frag_count[k] are never read: they may hold bytes that arrived but were not agreed on. The application's own proposal for that round is at node self_index — in the host's own queue, not in the ring. Everything the host needs to do this is in the record and in the pages; it never has to read a CSR on the fast path.

Why a prefix. On one link frames arrive in order, so a gap means a loss. If fragments past a gap were counted, one lost fragment and one repeated fragment would add up to "all of them". So a repeat, or anything after a gap, is simply not counted. It is still staged and DMA'd — placement is by frag_idx — but no agreed prefix will ever cover it, and the host never reads past frag_count. Our own fragments are counted at admission: our bytes are already in our own host memory, nothing has to land.

The event rules

  • open(R): at every boundary slot R mod 4 is cleared and R becomes the open round. The pulse is the core's ungated round_start_pulse — pure timing — so the round a node is activated in is open too. Opening is the only eviction; nothing counts it.
  • fragment staged(node, R, idx): if R is the open round and idx == count, count += 1; a repeat or a fragment past a gap changes nothing. If R is not the open round the fragment is late: PRES_LATE += 1. ssr_rx_engine already refuses payload for any other round, so "late" here can only be a fragment admitted just before a boundary whose last beat is stored just after it. The transmit cutoff is sized so that does not happen; this counter is how you would see that it did.
  • local sent(R): count[self] += 1 if R is open, else late.
  • error(R, node): if the slot holds R, set failed (PRES_ERR += 1); else PRES_ERR_MISS += 1, the round has already gone.
  • Same-cycle ordering: the counts are written, then an opening clears its slot. The open round moves on the same edge, so a fragment landing on the boundary cycle itself is counted into the round it belongs to, which is still the open one.

Two outputs, three customers

o_prev_ack is our vector about the round before the open one, node k at bits [8k +: 8], zero until that round has been held. It is re-read from the slot every cycle rather than latched at the boundary, so a fragment counted on the boundary cycle is in it. It feeds ssr_tx_engine (the ack field of our next control frame) and ssr_rx_engine (the vector a peer's must equal). The counts for R are final at the boundary into R+1 — the receive round filter drops anything later, and the cutoff makes sure nothing legitimate is later — so the value our control frame carries at 332 ns, the value the ack rung compares against until 646 ns, and the value the verdict record reports are one and the same.

Query B is the verdict writer's: given a round that has just been committed, return whether the slot still holds it (hit), present (bit k: no DMA error for (R, k)) and the eight counts, which become the record's frag_count[]. Four slots is enough because a round is queried less than one round after it closed, and the fence (Section 11) can add at most the DMA drain time; the slot is not reused until R+4.

What "stored" means, and one consequence

The tracker counts ssr_payload_stage.o_staged, which pulses only when a frame has been written into a free slot and committed. A frame the ladder accepted but the stage discarded for lack of a slot is not counted. So if the host stops taking delivery (turns payload DMA off, or lets PCIe stall) for more than sixteen frames, this node's counts fall short of what the others hold, its vector disagrees with everyone's, and at the next decision it has no witness but itself and halts with HALT_NO_AGREED_ROW. That is the honest outcome — the node really does not hold what the others hold — and it is tested end to end (case H4 in Section 14). A DMA error is different: the frame was stored, so it is counted, and only present_set records the loss (Section 11).

SECTION 10The core: witnesses, the sound set, the decision

ssr_core.v (ssr_core) owns time and the decision. It computes round_id from PTP, raises the boundary pulse, exports the windows and the state the receive ladder judges against (run_id, round_id, sound set, control window, payload enable), gives the transmit side its start pulse and the o_tx_pay_open level that falls at the cutoff, keeps the two-stage pipeline, and once per round — at the control deadline, o_ctrl_end_pulse — evaluates the PREVIOUS stage. It does not filter frames — that is the ladder's job, applied once — it does not touch payload, and it never handles a count.

The witness mask

For the round in PREVIOUS the core keeps one bit per node, previous_stage_witness_reg. At the boundary that makes a round PREVIOUS the mask is set to ourselves alone; after that every o_rx_valid pulse from ssr_rx_engine sets the sender's bit — a peer control frame that cleared every rung, the last of which was "its ack vector about this round equals ours". At the control deadline — a control frame later than this is dropped, so nothing can still add a witness — the evaluation reads the mask combinationally:

  1. Witnesses. witness_mask = previous_stage_witness_reg & current_sound_set & members. A trusted pulse from a node already dropped cannot count — the ladder drops its frames anyway, and the AND makes it true by construction.
  2. Agreed. If we are still in our own current sound set and popcount(witness_mask) ≥ QUORUM = N/2 + 1 = 2, our own ack vector for that round is agreed. The core does not hold that vector; it lives in the tracker.
  3. Sound set. The witnesses are the new sound set — the nodes that hold what we hold. It is a subset of the old one by the AND, and contains us.
  4. Outcome. Commit: o_commit_valid pulses with the round id and o_commit_set = the new sound set; the sound set is installed; COMMIT_COUNT increments. What was committed of each node is our own count for that round, which the verdict writer reads from the tracker. Halt: the state goes to S_HALT, the reason and the witness mask are frozen in the HALT_* registers (HALT_WITNESS), and the node is silent until software reboots it.

There is no separate "is the agreed set deliverable" check any more. The old bit-row design needed one because the agreed row could name a node whose proposal had not reached this host; here what is agreed is our own vector, which we hold by definition.

What committing a prefix means

A node's round is no longer all-or-nothing: the committed count for node k can be smaller than what k sent — as on the right above, or when k crashes after its first few fragments reached everyone. In every such case k is not a witness, so k halts or is already gone; a healthy node's round is still all-or-nothing in practice. With fragments sent mid-round, "how much k meant to send" is not something anyone else can know, so what the cluster agrees on is what it holds. A committed prefix ends on a ring-entry boundary, which is why a proposal never spans two entries.

State, activation, halt

Four states: S_IDLE (disabled, or timing not yet armed), S_WAIT_ACTIVATE, S_RUN, S_HALT. Software writes a configuration — run_id, membership bitmap, effective_round — and pulses activate; at the first boundary with round_id ≥ effective_round the core installs it, resets the pipeline (the activation round is collected, and is decided at the next round's control deadline — one priming round), and runs. Activation also works from S_RUN, so a live cluster can take a new membership without stopping. It never lifts a node out of S_HALT: a halted node must be rebooted, and then reactivated with a fresh run_id, otherwise it would rejoin reusing round ids it has already spoken for. A PTP step, a backward jump or a lost lock is a timing fault and halts the same way (HALT_TIME_FAULT).

SECTION 12The wrapper: DMA paths, registers, bring-up

ssr_dataplane.v is where the modules above meet Corundum. It wires the modules to each other and to Corundum's interfaces, instantiates ssr_csr — the one place every register lives — and checks at elaboration that the parameters fit together.

Two DMA write paths

The wrapper does not share the DMA write path at all: the app block has two, and each writer gets one. What decides which writer goes where is how mqnic_core.v merges them into its single PCIe DMA engine.

Elaboration checks

Verilog initial blocks in the wrapper refuse to elaborate a configuration that cannot work, rather than letting it fail silently at run time: a full round's budget of paced fragments must start by the transmit cutoff (TX_LAST_START_NS ≤ TX_PAY_CUTOFF_NS, 3 086 ≤ 3 341), or P_FRAGS_PER_ROUND — which sizes the host regions — would promise a round the link cannot carry; P_NODE_COUNT ≥ 2; the staging ring must fit one ram_sel (16 × 4096 ≤ 2^16) and hold a round of peers (P_PAY_SLOT_COUNT ≥ (N−1) × P_FRAGS_PER_ROUND); the payload tag range must fit the app's tag width. ssr_tx_engine and ssr_rx_engine each check that their payload bound equals SSR_FRAG_BYTES, and ssr_core that the cutoff lies between our control frame and the end of the round.

The registers: one module, one page

Every register the host can see is in ssr_csr.v, one 4 KiB page decoded once. No other module has a register bus: a setting reaches its module as an input port (ssr_core's i_cfg_*, the proposal reader's i_ring_base, the writers' i_enable), and whatever the host may read comes back as an output port. ssr_csr.v's header is the table; kernel/ssr_regs.h and the cocotb driver copy it.

  1. Read TYPE and VERSION; read NODE and ROUND_NS and check them against the cluster plan; read GEOMETRY and PAGE_BYTES and allocate the two rings: 2^host_depth × N × 2^region_shift bytes for payload, 2^verdict_depth × 64 for verdicts.

  3. Write CFG_RUN_ID (fresh, never reused), CFG_MEMBERSHIP (0b111), CFG_EFF_ROUND (a round a few milliseconds ahead, the same at every node); write CORE_CONTROL = enable | activate. Watch CORE_STATUS: timing armed, PTP valid, activation pending → cleared at the effective round.

  5. On a halt: CORE_STATUS.halted is set; read HALT_REASON, HALT_ROUND, HALT_WITNESS; write CORE_CONTROL = enable | reboot; reconfigure with a new run_id and re-activate.

SECTION 13Failures, replayed end to end

Each of these is a scenario the integration bench runs. Following one through every module is the best way to check you have the model right.

13.1 A peer delivers fewer fragments than it sent (H1)

Node 1 sends 3 fragments in R, but the third is lost on the way to every receiver — its own transmit path dropped it, say. ssr_rx_engine: the two that arrive pass the ladder. ssr_presence_tracker at nodes 0 and 2: count[1] = 2. At node 1: count[self] = 3, because it counts what it sent. R+1's control frames: nodes 0 and 2 carry [2, 2, 0], node 1 carries [2, 3, 0]. At node 0, node 2's frame clears the ack rung and node 1's fails it (RX_ACK_DISAGREE += 1). core at R+1's control deadline: witnesses {0, 2}, a quorum → commit, sound set {0, 2}; node 1, with no witness but itself → HALT_NO_AGREED_ROW. verdict at node 0: frag_count [2, 2, 0], present_set 0x07, commit_set 0x05: the host reads node 1's two pages — its prefix is committed — and knows node 1 left in this round. The third page was never written; it would not be read if it had been. From the decision on — still inside R+1 — node 1's frames fail the sound-set test at the survivors (RX_SOUND_DROP). Had only node 2 lost the fragment, it would be node 2 whose vector differs from both others, node 2 that halts, and nodes 0 and 1 that commit all three.

13.2 A page's DMA fails (F4)

The write engine returns tag 7 with a non-zero error. ssr_dma_tag_pool: the tag is freed like any other, o_cpl_error with meta {R, node 1, slot 4}. ssr_payload_dma_writer: PAY_ERR += 1, slot 4 released to the stage, error pulsed to the tracker. ssr_presence_tracker: failed[R][1] = 1; the count is untouched. The ack reports what arrived on the wire, not what reached the host, so nothing about the protocol changes and the cluster commits node 1's three pages as usual. But the record for R is fenced behind that very completion, so by the time the writer asks the tracker the bit is set: frag_count[1] = 3 with present_set 0x05 — the "loss to count" case, and exactly what the bench's F4 asserts. It no longer matters whether the error lands before or after the boundary; the bit-row design's two cases are now this one. Either way the verdict never claims this host holds a page it did not get.

13.3 The host stops taking delivery (H4)

Payload DMA is disabled (or PCIe stalls) for longer than sixteen frames. ssr_payload_stage: STAGE_FULL climbs, frames are discarded, o_staged stops pulsing. ssr_presence_tracker: discarded frames are not counted, so our counts for the peers fall short of what they hold of each other. ssr_rx_engine: both peers' vectors differ from ours and fail the ack rung. core: one witness, ourselves → HALT_NO_AGREED_ROW. A node that cannot store what the cluster is agreeing on stops rather than lie. Recovery is a reboot and a new run_id.

13.4 A late control frame (E10)

Node 2's control frame for R arrives at 700 ns, after the 646 ns deadline. ssr_rx_engine: RX_CTRL_LATE += 1, dropped. What is lost is node 2's ack about R−1, so node 2 is not a witness for R−1. Nothing else is lost: node 2's fragments for R are still counted, because a round is opened by the boundary, not by a frame. core at the deadline: witnesses {0, 1}, still a quorum, so R−1 commits and node 2 leaves our sound set — a late control frame costs its sender its place, not the round. If node 1 did hear node 2 in time, node 1 keeps node 2 while we drop it: both commit the same vector for R−1, and sound sets may legitimately differ between nodes (docs/count_ack.md §10). On hardware a non-zero RX_CTRL_LATE means P_CTRL_PERIOD_NS is too short for the real link.

13.5 Halt and reboot (H2, H3)

While halted the core exports rx_pay_enable = 0 and an empty control window, so every incoming frame lands on RX_WINDOW_DROP or RX_CTRL_LATE and nothing is transmitted — a halted node is silent and deaf. Software reads the HALT_* snapshot, pulses reboot, writes a new run_id and membership, and activates. The pipeline primes for one round, the peers (still on the old run) drop our frames on RX_RUN_DROP until they are reconfigured too, and delivery resumes with the verdict seq continuing from where it was — the host uses SEQ at 0x318 to resynchronise.

One-sided negative controls

A bench that passes proves little unless it is known to fail when the design is wrong. Each bench therefore carries controls: a define that mutates the RTL in one specific way — remove the fence, count received instead of staged frames, feed the verdict writer the data DMA's completions, drop the page offset — after which the bench must fail on the checks that claim to cover that behaviour, and only those. Among them: CTRL_END_SETTLE_CYCLES = 1 in ssr_core.v, after which the trusted pulse from a control frame taken on the deadline's last admitted cycle is missed, the peer leaves the sound set, and case I3 fails; and the two that came with count acks — drop the ack rung in ssr_rx_engine (E14 and H1 fail), and count a fragment whatever its index in ssr_presence_tracker (an injected repeat is counted, the vectors disagree, the node halts). The controls are one-sided on purpose: they mutate the RTL, never the bench's expectations, so a control that still passes means the bench is not looking. The header of each bench lists its controls and the expected failure count.

Discipline the benches follow

  • Bounded waits: every wait has a timeout that fails the bench, so a hang is a failure and not a stall.
  • Sample after the non-blocking assignments (#1), never on the edge; AXI drivers sample tready at the edge.
  • The receive port has exactly one driver process (the peer driver), which also plays the injection cases, so frames never interleave on the port.
  • The integration engine model keeps a queue of 64 descriptors per DMA path and, like Corundum, serves the control path (the verdict) first, reads staging RAM through a pipelined producer/consumer per segment (four pages a round would otherwise fall behind), holds completions on request to test the fence, and can force an error on a chosen (node, delay).

The cocotb harness under tb/mqnic_core_pcie_us/ (ssr_packet.py, ssr_verdict.py, ssr_sim_harness.py, ssr_dataplane.py) mirrors the wire and record formats in Python and drives the same wrapper inside the full mqnic core; its Makefile builds the core with the AU200's own parameters (two interfaces, 1 024-bit RAM rows, 13-bit app tags, 48-bit timestamps, BAR2 and the interface streams on; docs/au200_parameters.md derives each one), and five tests pass end to end through Corundum's real PCIe DMA engine and MAC: run_test_ssr_dataplane (the node joins, rounds are decided and delivered with the peers' pages byte for byte, our proposals leave as fragments, control frames sent at 332 ns reach the ladder by ~400 ns), run_test_ssr_backlog (24 proposals across a ring wrap, five a round), run_test_ssr_short_peer (case H1 through Corundum), run_test_ssr_halt_recover (halt, then the driver's reboot and fresh run id) and run_test_ssr_nic_coexist (host traffic on both interfaces while the protocol runs); run_test_nic, Corundum's own, passes alongside. kernel/ssr_regs.h carries the register constants for a future Linux driver.
