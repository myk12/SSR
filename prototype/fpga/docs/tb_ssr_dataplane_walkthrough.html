Reading the dataplane from its own waveform

How to run tb_ssr_dataplane and get the whole run as one FST file, what every section of the bench does, what every test case sets up and asserts, and where in the waveform to look — with the real times from a run.

How to use this

Section 1 gets you a waveform. Section 2 is the anchor: one healthy round, every event with its offset in nanoseconds, measured from the dump — memorise those numbers and every other round in the file reads itself. Section 3 goes through the bench source in order, so you know which signals are the bench's models and which are the DUT's. Section 4 is the test-by-test walk: for each one, what it does, what it checks, the time to jump to, and the signals to add. Section 5 has the signal paths grouped per module, ready to paste into Surfer's filter.

Times in this document come from the node-0 build. They move by a few microseconds when the bench changes; the banner of each test prints its exact start time (in picoseconds) in the log, so grep the log if a number here is off.

SECTION 1Run it and get the waveform

Everything runs from prototype/fpga/tb/ssr_dataplane. Three ways to run the bench:

make tb_ssr_dataplane             # the run, VCD of the whole hierarchy (default SSR_WAVE=+dump), ~1.5 min
make tb_ssr_dataplane SSR_WAVE=   # no waveform, fastest
make tb_ssr_dataplane_fst         # the WHOLE run, every signal, as build/tb_ssr_dataplane.fst (25 MB)

Use the FST target for Surfer. The run is 1.87 ms of simulated time; as a VCD of the full hierarchy it is about 900 MB, as FST it is 25 MB and opens in a few seconds. NODE_ID=1 or 2 builds the bench with the RTL playing that node instead (the peers' ids are derived from it). The bench prints ALL TESTS PASSED and the check count at the end; the FST is complete whether or not the run passed.

cd prototype/fpga/tb/ssr_dataplane
make tb_ssr_dataplane_fst
surfer build/tb_ssr_dataplane.fst

Two more targets exist for narrower dumps, useful when you want a VCD:

make tb_ssr_dataplane_wave DUMP=dump FROM=196 FOR=14    # full hierarchy, from 196 µs, for 14 µs → 17 MB VCD
make tb_ssr_dataplane_wave                             # wrapper boundary only, whole run

In Surfer

  • The hierarchy is tb_ssr_dataplane (the bench's own signals: peers, engine models, host memory, counters) → dut (ssr_dataplane) → one instance per module: csr_inst (every register), core_inst, tx_engine_inst, proposal_dma_reader_inst, proposal_buffer_inst, ssr_tx_mux_inst, ssr_rx_demux_inst, rx_engine_inst, payload_stage_inst, payload_dma_writer_inst (with pool_inst inside it), presence_tracker_inst, verdict_dma_writer_inst.
  • Type a name fragment in the signal filter; Section 5 lists the signals worth adding for each module. Right-click a vector → format → decimal for round ids, counters and pointers; hexadecimal for addresses and tags; binary for bitmaps (previous_stage_witness_reg, commit_set, o_unit_idle), hexadecimal for ack vectors (o_prev_ack: one byte per node, node k at bits [8k +: 8]).
  • Jump to a time by typing it into the time box: the tests' start times are in Section 4, in microseconds. One round is 4 000 ns; tb_ssr_dataplane.dut.core_inst.round_offset_ns (decimal) tells you where in a round you are.
  • Add tb_ssr_dataplane.test_name (format: ASCII) and test_number (decimal) first: at every banner the name becomes the test's title and the number steps by one, so you can read which test a region of the waveform belongs to.

Two things that differ from the guide's timeline, and why

The bench's peers speak at 10–20 ns, not 332 ns, and their fragments follow back to back with no pacing: the peer driver sends the moment the control window opens and does not model a wire. So the receive side sees the whole round's traffic in the first 1.1 µs. Nothing in the DUT depends on that — the ladder judges kind, run, round, window and ack, not arrival time — but do not read the bench's arrival times as the protocol's. (Our own transmit side is paced for real: a fragment is 64 beats, 256 ns on the 512-bit bus, then the 328 ns pacing gap, so our starts are 592 ns apart here, not the 655 ns of a 100 Gbit/s line.)

The addresses: the writer computes region_index = (R mod 256) × 3 + k from the tag on the slot. 2 750 050 mod 256 = 98, so peer 1's region is 295 and peer 2's is 296; with PAYLOAD_BASE = 0x9_0000_0000 and a 32 KiB region, peer 1's page 0 is at 0x9_0000_0000 + 295 × 0x8000 = 0x9_0093_8000 and page 1 at +0x1000. Check payload_dma_writer_inst.region_index (decimal) and page_off (hex) on each issue cycle.

What this round shows that the old design could not

Entries posted 78 ns into a round are on the wire by 2 984 ns of the same round. Under the announcement design the engine sampled the buffer once, at the start pulse, and these four would have waited for round 2 750 010. The two things that make it work are visible above: the engine admits a fragment whenever a committed slot is offered (pay_accepted is a level test, not a plan), and the window stays open until 3 341 ns, sized so that a fragment starting at the cutoff still reaches a peer before its boundary.

SECTION 3The bench, section by section

The file is organised as nineteen numbered sections; this walk follows them in order. Line numbers are those of the current file. The rule to hold on to: everything under tb_ssr_dataplane.* is a model or a monitor; everything under tb_ssr_dataplane.dut.* is the RTL. The bench reaches into the DUT for timing stimulus — dut.round_start_pulse, dut.current_round_id / core_rx_run_id, dut.rx_ctrl_window_from_core, dut.core_tx_pay_open (B7 waits for the cutoff), and dut.core_inst.state_reg / round_offset_ns — and in one place for an expected value: the transmit monitor checks each frame's round and run against dut.core_tx_round_id / core_tx_run_id. The peers' ack vectors are not read from the DUT; the bench computes them from what it saw on the ports (§13).

Header comment (lines 5–202)

Four things worth reading before the code: the coverage map (which test proves which module property — the reverse index of Section 4), how the receive port is driven (one process owns it; tests inject through request registers), the negative controls (nineteen one-line RTL mutations and the failures each must produce — the bench's proof that it is looking; the two added with count acks are "drop the ack rung" in ssr_rx_engine, which E14 and H1 must catch, and "count a fragment whatever its index" in ssr_presence_tracker, after which an injected repeat is counted, the vectors disagree and the node halts), and the build knobs (SSR_TB_NODE_ID, SSR_TB_SOAK_ROUNDS, SSR_TB_IF).

§1 Geometry and configuration (206–337)

Every number the DUT is built with, recomputed here so the bench has its own copy to check against (A2 confirms the two agree). They are the AU200 build's: two interfaces (SSR on SSR_IF, 0 unless built with -DSSR_TB_IF=1, which the node-1 build is), a DMA RAM row of two 512-bit segments — two beats, beat k of a slot in segment k mod 2 of row k/2 — 13-bit app DMA tags (pages 0..15 on the data DMA, the verdict 0 on the control DMA), a 1-bit ram_sel (always 0: each DMA path's read port has one reader), 48-bit interface timestamps and a 96-bit ToD. The ones you will use when reading waves:

  • NODE_ID from the build knob; PEER_A/PEER_B are the other two ids in ascending order (node 0 → 1, 2; node 1 → 0, 2; node 2 → 0, 1). SELF_BIT, PEER_A_BIT, PEER_B_BIT, ALL_MEMBERS = 0b111 are the bitmap forms used in every expectation.
  • ROUND_CYCLES = 1000, CTRL_CYCLES = 161: the units every wait uses.
  • SLOT_BYTES 4096 / FRAG_BYTES 4032 / FRAG_BEATS 63 / SLOT_BEATS 64; PAY_SLOT_COUNT 16, ROUND_DEPTH 4, HOST_DEPTH_LOG2 8, REGION_SHIFT 15, REGION_PAGES 8.
  • The three host addresses, chosen far apart so a wrong one is obvious: proposals at 0x2000_0000, the payload ring at 0x9_0000_0000, the verdict ring at 0xA_0000_0000.
  • RUN_ID_A = 0x77 for the whole run until H3, RUN_ID_B = 0x78 after the reboot.

§2 Register map (338–450)

Every register address the tests touch, as localparams named REG_<name> after ssr_csr.v's map: one 4 KiB page, identity at 0x000, consensus at 0x100, the proposal ring at 0x200, delivery at 0x300, counters from 0x400. Nothing here is logic; it is the driver's view of the device. CORE_CTRL_ACTIVATE = 3 is enable|activate, CORE_CTRL_REBOOT = 5 is enable|reboot; the ring is REG_PROP_PRODUCER (the doorbell), REG_PROP_CONSUMER, REG_PROP_FETCH, with PROP_CTRL_ENABLE/FLUSH/CLEAR_ERROR as bits 0/1/2 of PROP_CONTROL and PROP_ST_* naming the PROP_STATUS bits. REG_FAULT is the one register every test wants at 0. New with count acks: REG_RX_ACK_DISAGREE (0x4B0, read by the counter model) and REG_HALT_WITNESS (0x14C, defined but not yet read by any test); REG_PRES_EVICT is gone with the counter.

§3 Clock, reset, time of day (451–478)

A 250 MHz clock and a PTP time-of-day counter that starts at second 11, ns 0, and advances 4 ns per cycle once time_advancing is set. It is packed into the 96-bit Corundum ToD format {sec[47:0], ns[31:0], frac[15:0]} as ptp_ts_tod and fed to ptp_sync_ts_tod, where the DUT reads its time; ptp_ts_rel (64 bits, total ns + frac) goes to the relative port, and port_ts (48 bits, {ns[31:0], frac}) is what the port model stamps on completions. This is the only clock in the cluster: the DUT derives its round from it, and the peer driver times itself off the DUT — which is why there is no skew in this bench.

§4 Scoreboard primitives (479–527)

check(cond, msg) counts every call and prints ERROR: with the sim time on failure; nothing stops. banner(title) prints a test's start time, bumps test_number and copies the title into test_name — a 160-character packed vector, not a string, because Icarus does not dump strings into a VCD/FST. wait_rounds(n) is n × 1000 cycles. goto_midround waits for the next boundary and then half a round — "a quiet moment": the peers have spoken, nothing is arriving, the next boundary is 2 µs away. Tests use it before reading counters so a frame in flight cannot make a count off by one.

§5 CSR bus (528–573)

A minimal driver for the wrapper's register interface: set address and data at a negedge, raise wr_en/rd_en, sample the ack on the posedge (#0.1 after it, so registers have settled), give up after 32 cycles. csr_expect(addr, want, name) is the read-and-compare most counter checks use.

tb_ssr_dataplane.csr_addr / csr_wdata / csr_wr_en / csr_rd_en / csr_rdata (hex) show every register access. A cluster of them marks the start or end of a test.

§6 DUT signals, §7 the DUT (574–1023)

The wires and regs for every port of ssr_dataplane, named from the bench's point of view: rd_desc_*/rd_status_* are the proposal DMA read descriptors and their completions; wr_desc_*/wr_status_* the data DMA's write descriptors (pages) and theirs; cwr_desc_*/cwr_status_* the control DMA's (verdict records); wr_* the segmented RAM write port (the proposal engine writes entries into ssr_proposal_buffer through it); cram_rd_* the data DMA's RAM read port (the write engine reads pages back through it); ccram_rd_* the control DMA's (it reads the record); host_tx_* host frames into the mux; port_tx_* what leaves for the port; port_cpl_*/if_cpl_* transmit completions in and out; peer_* the receive port (the peers); hostrx_* what the demux forwards to the host. All of those are SSR's interface. The DUT's interface ports are two lanes wide, so the bench builds the two-lane buses dut_s_axis_if_*/dut_m_axis_if_*: lane SSR_IF carries the signals above, lane OTHER_IF the other interface's otx_*, ocpl_*, orx_* (_s_ into the app block, _m_ out of it). The instantiation passes the §1 parameters and ties off what a lone app block does not need (ptp_td_sd, PPS, perout).

§8 The proposal ring and its read engine (1024–1185)

The host side of the proposal path, as a driver does it. post(n) writes n entries into the ring at the host's producer index (ring_seq[pos] remembers which absolute entry sits at each ring position), appends them to exp_q — entries leave in posting order, however the reads complete — and writes the new index to PRODUCER: the doorbell. The ring is 16 entries (PROP_DEPTH_LOG2 = 4), so the B and G tests wrap it.

The model of Corundum's DMA read engine is two processes. Accept (an always block): every descriptor is checked — length a slot, ram_sel 0, and dma_addr exactly the ring position of entry fetch_expect, so the reader must walk the ring in order — then parked in a 16-entry table with a random latency of 100..300 cycles (0.4..1.2 µs, a PCIe read). Complete (an initial loop): whichever parked read expires first writes its 32 RAM rows — 64 beats, two to a row, both segments at once — into the DUT's RAM and returns its tag on rd_status_* — so completions come back out of order, as they do from the real engine. Each beat is host_word(entry, beat), {5A, lane, beat, A0+entry} in every 32-bit lane, with entry the absolute index, so a wrapped ring that sent a stale entry fails. Beat 0 is filled too, on purpose: if the transmit path ever sent beat 0 the monitor would see it. rd_force_error_entry makes that entry's read fail (G1). prop_ring_setup is the four CSR writes of start-up; prop_wait_not_pending waits for a flush or clear to be carried out.

§9 Host transmit frames (1186–1232)

The NIC's own traffic, for the mux tests: 3-beat frames with pattern {C3, lane, beat, f}, the last beat 16 bytes wide, tagged 0x8000 | f in tuser — top bit set and an index below it, as Corundum's tx_engine tags a host frame — so the mux must forward their completions. host_exp_q remembers the order sent; the transmit monitor checks the order and every byte at the port.

§10 Port model (1233–1283)

Two things a MAC does. port_tx_tready is 1, or random 80 % when tx_bp_enable is set (B6). And one completion per frame: the tag from tuser[16:1] and the 48-bit timestamp at the last beat (port_ts) are queued, and returned on port_cpl_* four cycles later. The model keeps its own counts of SSR completions (tag 0x4000) and host completions, and the timestamp of the last SSR one, so B3 can compare the DUT's TX_CPL_TS against a value the DUT could not have invented.

§11 Transmit frame monitor (1284–1448)

Every beat that leaves the port is judged here, continuously, in all 49 tests. On a header beat it decides SSR or host by the tag. For SSR: ethertype, node id, round and run against the core's registers, zero padding, and the retired bytes — 15 (the old row) and 34–35 (the old frag_count) — zero. A control frame must have length 0, frag_idx 0, end on the beat, and ack bytes past the cluster zero; and, when it follows the previous round's control frame directly, its ack[self] must equal the number of fragments the monitor saw go out in that round. A fragment must carry an ack of zero, length 4032, the next frag_idx in order (0, 1, 2 … since the round's control frame) and below the budget of 5, the same round as its control frame, and the monitor pops exp_q to learn which entry it must be; it also adds one to dut_frags[round mod 16], which is what the peers put in their acks about us (§13). On every payload beat: tkeep full and tdata === host_word(entry, beat + 1) — payload beat k is slot beat k + 1, slot beat 0 never appears — and the frame must end on beat 62. An SSR frame, once started, must have tvalid high on every cycle until tlast (a gap is counted in ssr_tx_bubbles): a frame with gaps takes longer than the engine budgeted and could miss the cutoff. When a control frame goes out the monitor also files the round just ended's fragment count in last_round_frags / last_frags_round and fires ev_ctrl_frame, which B7 and B8 wait on. (The check it replaced, "a round sends what its control frame announced", went with the announcement.) Host frames are matched beat by beat against host_frame_word with their tag and final tkeep preserved.

§13 Receive port driver (1465–1766)

The largest model, and the one process allowed to drive peer_*. Three parts:

  • peer_word(node, round, frag, beat) is the payload pattern, a function of all four so a page holding the wrong node's, round's or fragment's bytes fails loudly. send_rx_frame(...) builds a 64-byte header from its arguments (every field settable, including a length that lies and a tkeep that is short) and streams beats payload beats after it; it also records the frame in rxrec_* for the host-RX sink to compare against, and notes the round_offset_ns at which the header beat was taken (inj_hdr_offset_ns, for I3). send_peer_ctrl and send_peer_frag are the two well-formed shapes.
  • The peers: peer_mask (who transmits; everyone but us), peer_zero_mask (sends its control frame and no fragment), peer_short_mask (delivers one fragment fewer than it believes it sent), peer_frags (2 for the whole run except I2, where it is 1), peer_ack_xor[] (bits flipped into a peer's ack — a peer that disagrees; zero by default). The peer_driver block wakes on dut.round_start_pulse, zeroes the new round's bookkeeping, waits for the control window (bounded, so a halted DUT gets silence), then sends every peer's control frame, then every peer's fragments, for the round id it read from the DUT.
  • The peers' ack vectors are computed, not configured, so a peer is trusted exactly when a real one would be. For each (node, round mod 16) the driver keeps peer_deliv — fragments a peer actually put on the wire, which is what every other node holds of it — and peer_claim — what the peer believes it sent, its own ack byte; the two differ only for a short peer. The monitor's dut_frags is what we sent. model_ack(j, r) builds peer j's vector about round r from those: its own claim, the other peer's deliveries, and our count. With nothing lost it is exactly our own vector. peer_disagrees(j, r) predicts the ack rung's verdict, and each disagreeing control frame the driver sends is counted in peer_ctrl_disagree for the counter model (§17).
  • The injection slot: a test fills the inj_* registers (ethertype, node, kind, ack, run, round, length, frag idx, beat count, tkeep, bad-user) and raises inj_req; the driver sends it after the peers' frames — or right after the peers' control frames, before their fragments (inj_early, E14), or after the deadline (inj_late, E10), or with the header beat on the deadline's last admitted cycle (inj_edge, I3) — and clears the request. inj_ack_model makes the injected ack the sending peer's model vector about the previous round, XOR inj_ack: a correct ack (E10, I3) or one deliberately off (E14). inj_defaults resets it to "a well-formed fragment from PEER_A for the current round and run".

§15 The DMA write engine and the host memory model (1821–2170)

The model of Corundum's DMA write engine, and the host memory behind it. Descriptors are queued as offered, one queue per DMA path (64 deep each), and at acceptance the bench already checks them: a page descriptor must select the staging RAM, carry a pool tag, be one slot long and page-aligned; a verdict descriptor, on the control DMA, must select 0, carry tag 0, be 64 bytes, and read beat 0. For each page descriptor accepted, out_by_ridx[R mod 256] — pages of that round still outstanding, decoded from the address — is incremented; for each verdict descriptor accepted, a snapshot of that array is taken (snap_out), to be judged once the record's round is known. A page accepted on the same edge as a verdict counts as outstanding in that snapshot.

The engine loop takes one descriptor at a time, control first as Corundum does, and reads the bytes through that path's read port (ram_read_beats, told which port: a row at a time, a command only to the segments that hold wanted beats — both for a page, segment 0 alone for the record — each segment handshaken and collected on its own, fast enough for four pages a round), so both read ports and the ram_addr are under test. A record goes into the record cache (rec_key/rec_data, 16 entries) and is judged against its snapshot: a record offered while any page of its round was outstanding is a fence fault. A page goes into the page cache (pg_key/pg_data, 64 pages), possibly with a forced error (wr_force_error, per node, after a delay). Then the latency, the optional hold (cpl_hold, all completions), the optional park (park_req, one page's completion held while the rest go on), and the completion on that path's status stream: wr_status_* for a page, cwr_status_* for a record.

§17 The receive counter model (2242–2309)

Group E works by arithmetic. Every frame the peers send is parsed, and accepted unless it is a control frame whose ack disagrees; every injected frame is parsed, and either accepted or charged to exactly one rung. rx_verify(ctx) reads the ten ladder counters and compares each to peer_frames_sent + inj_parsed, peer_frames_sent − peer_ctrl_disagree + inj_accepted, exp_rung[RUNG_ACK] + peer_ctrl_disagree for RX_ACK_DISAGREE, and exp_rung[rung] for the rest. expect_rung(rung, also_accepted, ctx) bumps the expectations, injects, settles to mid-round, and verifies — one call per E case.

The record for that round is fenced behind the failing completion; when it lands: commit_set[B] = 1 and frag_count[B] = 2 (committed), present_set[B] = 0 (this host's copy is not intact), the others present. PAY_ERR +1, PRES_ERR +1, PRES_ERR_MISS 0 (the round was still held), no fence fault; the next record is whole again and STAGE_FULL never moved (the slot was released despite the error).

Group H — protocol failure and recovery

H1 · a peer that delivered one fragment fewer than it says: no witness, its prefix committed, out of the sound set1 742.1 µs

In one round S, PEER_B puts one fragment on the wire and believes it sent two — its own transmit path lost the last one (peer_short_mask). Everyone else holds the same prefix of 1, so in S+1 A's ack and ours agree and B's, which says 2, does not: exactly one disagreeing control frame, RX_ACK_DISAGREE, and B is no witness. Two of three is a quorum, so S commits — with B's prefix, the one fragment everybody holds — and the sound set shrinks to us and A. B, with no witness of its own, would halt there; the bench has it send its control frame and nothing else in S+1 (peer_zero_mask) and fall silent after. The record for S: commit_set = everyone but B (B left in this round), frag_count[B] = 1, present_set = 0b111 (the page B did send reached the host), A unaffected; B's one fragment is a committed page and its missing one has no page. Two rounds later CURRENT_SOUND_SET has lost B and kept us and A, the node did not halt, nothing was "malformed", and the ladder counters still agree with the model. The next record has B out with frag_count 0. Then one injected frame from B: RX_SOUND_DROP, and the sound set has not grown back.

Reading an ack vector

presence_tracker_inst.o_prev_ack, tx_engine_inst.ack_reg, rx_engine_inst.hdr_ack / i_rx_self_ack and the monitor's ctrl_ack are all 64 bits, one byte per node, node k at bits [8k+7 : 8k] — so in hex node 0 is the rightmost two digits. In the anchor round 0x020200 reads node 0: 00 (we sent nothing), node 1: 02, node 2: 02. o_prev_ack is about the round before the open one and moves one cycle after each boundary; it keeps its value through a quiet run like the anchor's, and changes when something does — in H1 it goes to 0x010200 (we hold one of node 2's), in C2 to 0x000200. The counts themselves live in an array the dump does not contain; pl_count and self_count pulse on each increment.
